## Independent findings

1. The checkpoint, manifest, task-set, predecessor, publication, trigger, and Job 4 completion identities are coherent. Progressions 1-3 made zero provider calls, the active `cera.active_runtime.d180.v1` profile remained unchanged, the repository-owned Scene Change control remained inactive, and no live story, production database, service, deployment, remote, or push effect occurred. The new implementation is additive and shadow-only as claimed.

2. Job 4 is terminal failed evidence, not a live qualification. It stopped at `pre_provider` with an `AttributeError`, observed 0 of the authorized 10 provider calls, accepted no disposable turns, created no scene summary, and left both the source and disposable SQLite hashes unchanged. Planner and Validator thread identities were never established. The retained Job 4 detail exposes only the exception type and a generic `pre_provider` stage; no per-turn debug directory, stack frames, failing operation, or safe attribute name was preserved. Consequently the root cause cannot be independently identified from the promised debug evidence, and none of the live stored-thread, structured-output, history-injection, rich-sequence, edit-package, Scene Change, quality, usage, or latency claims is qualified.

3. Progression 1 introduces a materially richer and more useful Planner sequence shape. The beat contract requires perception, goal, pressures, tactic, causal explanation, observable direction, private-state guidance, material continuity, resulting state, realization space, and protected-user allowance, and it rejects the simplest action-only form. The stable/dynamic prompt split, incomplete character-summary envelope, role-scoped world root, and append-once accepted-final envelope are coherent shadow mechanisms. However, `source_evidence_bindings` is currently only a tuple of provider-authored local strings. Python verifies syntax and uniqueness but does not bind those names to the current user source, an authorized ACTIVE file revision/hash, or an actual world-MCP read. Tests use invented labels such as `source_current_user` and `evidence_sakura_guarded` without an allocation or lookup receipt. A ready sequence can therefore appear evidence-grounded while citing no proven current source or fetched record. This is a material authority and knowledge-use gap, especially for private character state and rule/event recall.

4. The physical separation of continuous Planner and Validator sessions, their compatibility identities, role-specific directories, and path-deny policy are directionally sound. The accepted-final synchronization ledger also correctly distinguishes a Python ledger entry from model-visible history injection. The live implementation nevertheless depends on a private app-server `thread/inject_items` path that remains unqualified because Job 4 failed before session creation. That alone is an expected live gate, but the failure boundary is also incomplete: after a transport returns, continuous Planner/Validator/Composer decoding, bridge finalization, or domain validation can raise ordinary exceptions without consistently carrying `external_provider_calls_observed=1`, the safe provider receipt, or operation telemetry. The Job 4 counting wrapper relies on that metadata. A post-dispatch contract failure can therefore be recorded as zero calls even though one call occurred. Provider-call accounting must remain conservative and truthful on every failure path before another live run.

5. Progression 2's complete final sequence and revision-bound edit package are useful and preserve Python's mechanical promotion role. The 100-operation ceiling, created-field log, stable target paths, expected revisions, final-sequence provenance, and separate Scene Summary task are appropriate experimental controls. Its `False Positive` behavior is not compatible with CERA's existing D-177 creator-review semantics. Existing CERA permits False Positive only for publication-eligible Concern or Critical assessments and records verifier-owned diagnostic feedback. The new package permits `FALSE_POSITIVE` only when the assessment is Good and `accept_allowed`, making it functionally identical to ordinary Accept while rejecting the actual existing False Positive case. The provider-free test that treats a Good package as False Positive compatibility confirms the mismatch rather than preventing it.

6. Progression 3 mostly preserves candidate isolation: nonaccepting turn actions leave ACTIVE unchanged, ordinary accepted edits are applied to a candidate view with revision preconditions, and the exact accepted pair is stored before Planner synchronization. Scene Change has an unresolved authority classification. Pressing Scene Change is an explicit creator instruction to summarize, but the resulting Validator-authored summary is written directly into `ACTIVE/Scenes` and indexed before any separate review or typed promotion receipt. The code and documentation elsewhere describe ACTIVE as accepted world state and Validator packages as advisory until creator action. Either the Scene Change action must be formally defined as authorizing publication of a clearly non-authoritative, regenerable derived summary, or the summary must pass the same candidate/promotion boundary. The current combination silently changes the meaning of ACTIVE for this one semantic artifact.

7. The directory promotion is exception-safe in the narrow in-process case but is not restart-atomic as documented. `_promote_directory` writes a prepared journal, renames ACTIVE to a backup, then renames the prepared tree into place. It rolls back only when the second rename raises inside the running process. There is no startup recovery that examines a prepared journal or restores `PRIOR_ACTIVE` after a process or power loss between the two renames. Provider-free tests cover caught-exception rollback, not crash cut points. Calling this a restart-coherent atomic promotion overstates the implementation.

8. Two smaller contract claims also require tightening before sustained use. `create_file` allows a JSON string or array, but only object records receive `_cera_revision`; such files cannot participate in later revision-bound edits despite the stable-file contract. Debug redaction removes credential-like keys and strings beginning with `Bearer ` or `sk-`, but it does not redact credential tokens embedded inside a larger raw prompt or error string. The complete-debug requirement should not be treated as secret-safe until embedded-value cases and the pre-provider initialization path are covered.

9. The checkpoint's provider-free test totals establish deterministic behavior for the cases encoded, not semantic quality or live reliability. Several tests currently encode the disputed behavior—unallocated evidence-binding labels and Good-only False Positive acceptance—so the passing count does not resolve those defects. Compact v7 remains defective and inactive, and this review finds no reason to change that boundary.

## Required corrections

1. Make rich-sequence source/evidence bindings authoritative and auditable without restricting the creator's desired broad world-directory search. Python must allocate or derive request-local binding handles for the current source and exact ACTIVE file reads, including path, revision, content hash, world/branch identity, and applicable knowledge owner. Every Planner beat binding must resolve to one current authorized handle, and hard character/rule/event decisions must prove the corresponding read. Validator final-sequence items and world edits must retain traceability to valid Planner beats and those resolved bindings. Add negative tests for invented handles, stale revisions, sibling-branch paths, unread private records, and transferred private knowledge.

2. Correct provider-call failure accounting across every continuous role. Once transport dispatch occurs, all bridge-finalization, JSON decoding, schema decoding, domain validation, and post-response failures must conservatively preserve one observed call, the safe provider receipt or failure receipt when available, and operation telemetry. Job 4 must count calls from a durable ledger rather than trusting optional exception attributes alone. Add focused tests for Planner, DeepSeek, Validator, Scene Summary, and world-MCP finalization failures after dispatch.

3. Diagnose and fix the exact zero-call Job 4 `AttributeError` provider-free before another live attempt. Initialize a safe diagnostic record before stored-session/backend construction, preserve the exact owning operation and stack frames, and ensure terminal evidence distinguishes account setup, backend construction, stored-root materialization, session creation, world setup, and prompt setup. Do not infer the missing cause from the exception type. The failed Job 4 remains immutable and must not be relabeled as a canary pass.

4. Align `FALSE_POSITIVE` with the existing creator-review contract. Ordinary Accept handles Good assessments. False Positive must remain available only for the existing publication-eligible Concern/Critical case, accept the candidate unchanged through the normal gate, and create the existing verifier-owned diagnostic without becoming a story constraint. Reuse the current coordinator semantics instead of defining a second incompatible meaning.

5. Resolve Scene Summary authority explicitly. Preserve the creator's one-button Scene Change workflow, but either: (a) save the Validator summary as a labeled non-authoritative derived view that is reproducible from the exact accepted-turn allow-list and may be regenerated without changing accepted world truth; or (b) stage and promote it through a typed creator-authorized candidate operation. Do not write an unlabeled advisory summary directly into a directory whose other contents are described as accepted authority.

6. Implement restart recovery for candidate promotion or narrow the contract and documentation. Recovery tests must cover process loss after journal creation, after ACTIVE is moved to backup, after prepared ACTIVE is installed, and before journal completion. Recovery must deterministically restore the prior tree or finish the exact prepared tree by verified hashes; it must never leave ACTIVE absent or combine trees.

7. Restrict mutable `create_file` records to revisioned JSON objects, or define a distinct immutable file class that cannot later receive revision-bound edits. Strengthen debug redaction for embedded bearer/API-key patterns and ensure a complete safe debug skeleton exists for failures before the first turn recorder is created.

8. After these corrections, rerun the focused and complete provider-free suites, freeze a new checkpoint and review package, and request a separately identity-bound live canary. Do not patch and rerun the failed Job 4 under its existing identity.
