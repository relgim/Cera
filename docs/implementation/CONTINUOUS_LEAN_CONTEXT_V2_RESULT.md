## Outcome

V2 preserves the D-200 lean architecture while removing the remaining open
Planner authority-dictionary boundary. Python now constructs one closed,
discriminated turn packet only after ingress custody, evidence allocation,
stable-reference resolution, D-200 summary selection, and context-mode
classification are complete. The prompt builder accepts that validated object,
not a caller dictionary, and derives its mode metadata from the object.

The four turn packet identities are:

- `first_turn_initialization`;
- `lean_continuous_continuation`;
- `projection_assisted_continuation`;
- `scene_change`.

Physical-thread initialization remains separate and has three closed kinds:
`first_thread_initialization`, `reconstruction_initialization`, and
`accepted_checkpoint_fork_initialization`. Reconstruction and fork material
cannot enter an ordinary turn packet.

## Closed ordinary lean contract

The ordinary continuation contains the current source and trusted source-unit
custody, minimal scope identities, protected-user claims, request-local
evidence handles, selected changed summary bindings, a compact accepted-head
receipt, and value-free stable reference keys. It does not accept previous
pairs, prior complete sequences, accepted-session fact payloads, previous
prose, full history, unchanged summaries, duplicated stable instructions,
foreign reference payloads, reconstruction/fork/Scene Change/projection
material, or arbitrary caller fields. Exact field sets are enforced before
prompt assembly; nested mappings are closed and typed scalar payload slots do
not accept caller-owned containers.

The packet binds:

- current-source bytes to ingress and evidence hashes;
- source-unit spans and protected-user claims to the exact current message;
- summary descriptors to their exact request evidence bindings;
- compact-head scope and synchronization custody to every stable handle;
- Scene Change context by exact context hash;
- prompt telemetry, debug evidence, replay input, and candidate authority to
  the same canonical packet bytes and SHA-256.

## Provider fork, reconstruction, and Validator closure

The preferred accepted-checkpoint fork creates a distinct child physical
thread, validates the deterministic privacy boundary, rekeys accepted
references into the child branch, persists exact-once value-free descriptors,
and rebinds summary-delivery and snapshot custody. A child first-lean preflight
uses only child keys; parent and sibling keys fail. A non-forkable or lost
thread still reconstructs into a new physical thread from the bounded accepted
tail and then returns to lean mode.

After the Planner returns, the Progression 2 closure resolves only accepted
reference keys the Planner actually cited. The separate Validator receives
their exact values and complete owner, visibility, branch, ancestry, receipt,
thread, role, and source custody. Composer remains current-turn-only and
receives neither that Validator closure nor a precautionary prior projection.
