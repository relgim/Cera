1. EXECUTIVE CONCLUSION
=======================

The requested retry policy is supportable only as a stage-local, custody-aware
mechanism. It must never replay the complete user request after earlier stages
may have created a candidate, accepted story state, or a derived recording.

The intended product policy is:

  - one initial provider-stage attempt plus at most two retries;
  - three attempts total, with no fourth attempt, model substitution, or
    fallback;
  - retry only a typed provider-stage failure whose prior attempt is closed and
    whose effect boundary is proven;
  - if the third attempt fails, stop the branch and show a critical error that
    identifies Codex or DeepSeek and the exact failed stage;
  - make Retry visible in SillyTavern only while another attempt is safely
    authorized;
  - the current code flags 180 seconds only for second-or-later calls on the
    same physical Planner thread; whether that concern rule should extend to
    every role with meaningful session reuse remains a review decision;
  - classify first-thread calls and replacement-thread cold rehydration
    separately from later retained calls.

This checkpoint is not production-ready. The repository now has a tested
Planner manual-transport Retry path, a disposable-SillyTavern qualification
contract, terminal critical-error UI, a local two-action UI ceiling, and a
provider-neutral retry foundation. However:

  - the d43 generic retry correction candidate passed its author gates, but an
    independent parent-swap fault test found a stop-ship custody race; the
    follow-up correction and re-audit are recorded in Section 5;
  - the generic core is not wired into the six live runtime stages;
  - the real backend does not yet authoritatively enforce the shared three-
    attempt terminal contract for every stage;
  - non-Planner retry buttons are not yet implemented;
  - installed SillyTavern at E:\AIChatBot\SillyTavern has not been synchronized;
  - there is no successful live campaign from which retained-stage averages
    can be calculated.

The correct action at this checkpoint is review, not a live run, deployment,
installation sync, freeze, merge, or further provider dispatch.

2.2 Codex safety interpretation recommended for approval
---------------------------------------------------------

The phrase "retry a failure in the middle" is interpreted as retrying only the
failed provider stage from its exact frozen input. It is not interpreted as
replaying the complete HTTP request or rerunning already-completed stages.

The two retries are explicit, idempotent Retry actions. There is no hidden
automatic retry loop in production. A qualification harness may drive those
same explicit actions mechanically, but it must exercise the same backend-
issued identities and limits as the UI.

The backend, not the browser, must be final authority for:

  - whether Retry is eligible;
  - which exact stage input is reused;
  - whether the previous owner is retired;
  - whether any failed-stage effect exists;
  - how many attempts have occurred;
  - whether another attempt identity exists;
  - whether the chain is exhausted or blocked by ambiguity.

The browser may enforce the same two-action ceiling defensively, but that local
limit cannot replace the backend cap.

Only closed provider-stage failure classes are retry candidates. Semantic
rejection, ordinary validation findings, creator Decline, local configuration
failure, authorization failure, changed branch authority, storage/custody
conflict, and exhausted budgets are not provider Retry events.

An unresolved or possibly still-running dispatch is not retried. It enters a
blocked-ambiguous state until read-only reconciliation proves its disposition.
This prevents a duplicate charged call and prevents two outputs from competing
for one stage effect.

The implemented three-minute retained-Planner flag does not cancel the call and
does not make it retryable. Its expansion to other retained roles and its exact
measurement boundary remain review decisions. The present hard provider
transport-loss boundary is 600 seconds. The phrase "first call" also needs a
product definition: the first call on each physical provider/stage session, or
only the initial retained Planner-thread call. Treating every fresh/single-use
role invocation as exempt would make the concern rule meaningless for Luna,
Writer, Recorder, and Adult Filter.

6. RETRY STATE MACHINE AND RATIONALE
====================================

The generic target state flow is:

  input_frozen
    -> attempt_prepared
    -> dispatch_started
    -> result_frozen
    -> downstream_intent_frozen
    -> downstream_bound
    -> succeeded

A closed retryable failure instead follows:

  dispatch_started
    -> awaiting_owner_retirement
    -> owner_retired
    -> next attempt_prepared

After attempt 3 fails closed:

  owner_retired -> exhausted

If dispatch, ledger, input, authority, owner retirement, result custody, or
downstream publication cannot be proven:

  current phase -> blocked_ambiguous

Why these boundaries exist:

  - input_frozen prevents a retry from quietly receiving changed context;
  - attempt_prepared gives every attempt a unique session and ledger prefix;
  - dispatch_started distinguishes a possible charged operation from a local
    pretransport failure;
  - owner retirement prevents two provider processes or threads from remaining
    authoritative for one stage;
  - result_frozen prevents a successful provider call from being repeated after
    a local crash;
  - downstream intent/evidence makes stage publication idempotent;
  - blocked_ambiguous prefers a visible stop over a duplicate provider call;
  - exhausted closes the attempt chain and exposes no successor action.

The controller must be provider-free. It records and validates authority but
does not itself call Codex or DeepSeek. Runtime adapters supply exact input and
result bytes, evidence hashes, ledger prefixes, operation counts, durations,
and optional token metrics.

retirement and cannot advance to another attempt.

10. PRIVACY, CRASH, AND ACCOUNTING RULES
=======================================

10.1 Privacy
------------

  - Exact stage inputs and exact provider results belong only in protected
    checkpoint storage.
  - Public chain/status artifacts contain closed enums, booleans, nonnegative
    counts, and SHA-256 bindings, not prompts or prose.
  - Protected adult prose must never enter ordinary DTOs, client metadata,
    terminal panels, test output, or general debug logs.
  - SillyTavern receives only the safe terminal projection described above.
  - Error messages exposed by the proxy are fixed generic text, not raw provider
    output.

10.2 Crash and concurrency safety
---------------------------------

  - Every attempt has a unique session scope.
  - Exact input is immutable across all attempts in one chain.
  - A successful result is frozen before downstream work.
  - Restart recovery selects a provider-free action: dispatch a prepared
    attempt, resolve ambiguity, retire a closed owner, resume/reconcile
    downstream, replay success, report exhaustion, or report a block.
  - A crash-released OS lock prevents simultaneous process ownership without
    leaving a permanent lock after process death.
  - No-follow path checks, pinned identities, hard-link/reparse rejection,
    compact collision checks, atomic state writes, and immutable checkpoint
    hashes must fail closed.
  - If exact custody cannot be proved, stop; do not infer permission to dispatch.

10.3 Provider operation and token accounting
--------------------------------------------

  - A local pretransport failure consumes zero submitted and zero charged
    provider operations, but remains evidenced.
  - A submitted failed attempt remains charged.
  - provider_operations_observed counts operations proven by the ledger.
  - provider_operations_conservative includes any unresolved possible operation
    and may be greater than observed; it must never be lower.
  - An ambiguous dispatch must conservatively reserve an operation and block
    redispatch until reconciled.
  - Attempt and terminal totals remain cumulative across restart.
  - Optional input, cached-input, output, and reasoning token counts remain null
    only when genuinely unavailable; they must not be replaced with invented
    zeros.
  - Terminal attempts require a real duration; preterminal states may not yet
    have one.
